# Architecture and limitations

The dependency direction is `tools/cli → logics/core → logics/models`. Models define shared IDs, errors, snapshots and diagnostic results. Core owns configuration, policy, Pueue I/O, persistence, execution services and doctor. CLI parses argv, collects terminal approval, renders output and selects process exits. `logics/tests` contains contract/integration fixtures. Moon coordinates Cargo and the Rspress site; quality scripts live under `qualities`.

Pueue 4.0.4 performs actual background execution. axvern invokes its CLI with separated argv and `add --escape`; it does not pass target argv to a local shell. This is verified with Pueue's POSIX `sh -c` daemon shell. Arbitrary daemon shell customizations are unsupported. Pueue can still execute any approved program with your user privileges; axvern does not sandbox target programs or inspect wrapper scripts.

Execution IDs are `ex_` plus lowercase UUIDv4. Ownership matches canonical queue configuration path, integer Pueue ID, and creation timestamp. Deleted/recycled IDs cannot silently resolve to a different observed task. A daemon configuration must retain its target identity. Keep stores on a local filesystem with Unix permissions, reliable advisory locks, atomic rename, and fsync; network filesystems are unverified.

Registration and local persistence cannot be one atomic distributed transaction. A successful registration followed by a store error returns a recovery receipt. An interrupted/ambiguous registration requires nonce-label reconciliation; there is no automatic add retry. Killing the client does not kill a daemon job. Request IDs have durable pre-submission intent records. An unresolved intent is never resubmitted; manual queue-label reconciliation is required. Result bytes live separately from metadata and request records.

New CLI registrations run an internal axvern runner through Pueue. The runner starts the approved original or opt-in rewritten program without a shell, relays combined output to Pueue, reserves bounded private spool capacity, and atomically publishes its preview before exiting. Target failure and result persistence failure are separate. Status/wait return state and timestamps; result returns saved previews. Read retained logs with [`query`/`recall`](/retrieve), which stream Pueue's log file without running the command again. The internal bounded output probe reads up to 101 tail lines/8MiB response and reports truncation beyond 100 lines or the requested bytes; it does not silently claim a complete long log. stdout/stderr separation cannot be reconstructed from Pueue's merged output.

The internal runner entry (`axvern __axvern_worker …`) is not a supported interface. It is reachable by any local process that can run `axvern`, and it starts the program after `--` directly, without Policy evaluation or approval. It does not check the arguments against a stored request or plan. This grants nothing beyond what that process could already do with your user privileges, which is consistent with Policy not being a sandbox. Do not expose the `axvern` binary to principals you do not already trust with your user account.

Implemented: [v0.2 inspection/analysis](/discovery) and limited opt-in command replacement. Discovery adapters produce explicit argv, run through Policy/Pueue, normalize bounded streams, and share the result store. `fs analyze` groups child records and lazily publishes an aggregate, preserving successful sections when another fails. Future work includes v0.3 selective `query`/`recall` and later measurement/optimization workflows. Those future commands are unavailable. License, binary release destination, package registry, signing, and public hosting remain undecided. Nothing is published or deployed by the quality/release checks.
